# The trust tool

Talk to Gemma. After every turn, see what the NLA says the model was
representing — and which parts of that a sparse autoencoder can corroborate.

```bash
export NLA_REPO=/path/to/natural_language_autoencoders
python trust_tool/app.py --av $AV --ar $AR      # then open localhost:8000
```

On a card that cannot hold three 12B models at once, add `--phase`: each model
is loaded and released per turn. It works, and it costs a minute or two of
loading per reply.

Command line, over a stored corpus (not your own text — see below):

```bash
python trust_tool/trust_report.py --parquet acts.parquet --av $AV --ar $AR --n 5
```

---

## What you get per turn

| verdict | meaning |
|---|---|
| **CONFIRMED** | in the activation, **and** the AR recovers it from the explanation |
| **UNVERIFIED** | the AR produces it from the explanation; the SAE did not find it in the activation |
| **OMITTED** | in the activation; the AR does not recover it |

These are set operations on SAE latent sets — `F_orig ∩ F_ar`, `F_ar \ F_orig`,
`F_orig \ F_ar`. **The explanation text is never read**; it enters only through
the AR's reconstruction of it. No model judgement anywhere in the counts.

**UNVERIFIED means *not checked*, never *false*.** A latent lands there when the
SAE did not find it in the activation, which can mean it is absent — or that the
SAE cannot see it there. An SAE does not have a latent for everything.

**The counts include latents with no validated label.** Only labelled ones can be
named, and about half of all latents have one. A report showing "4 named of 15"
is stating its own coverage, not hiding anything.

## Where the activation comes from, and why it matters

**At the last token of your message** — the end of the conversation as it stands
just before Gemma starts generating. So the report answers: *what was the model
representing when it had finished reading you?*

On turn 3 that activation encodes turns 1 and 2 as well, because the whole
conversation is re-fed each time. Nothing is truncated: the activation at a
position already encodes every token before it, so a long conversation loses
nothing and simply runs until the context window fills.

### Why you cannot paste arbitrary text

The Gemma Scope 2 instruction-tuned SAEs are fine-tuned on chat data whose
assistant turns were **generated by Gemma itself** — from their paper, *"we take
open-source datasets of user prompts and generate responses from the
corresponding Gemma models."* Text from anywhere else is off that distribution.
This is not hypothetical: on FineWeb, out-of-distribution for the SAE, the same
pipeline measured a **7-point** effect where Gemma rollouts gave **25**.

Having Gemma write the conversation keeps the input in the distribution the SAE
was fitted to. You still choose the subject — by prompting, rather than pasting.

### Two honest caveats

- **The position differs from the experiment.** [RESULTS.md](../RESULTS.md)
  samples random positions *inside* Gemma's generated response. Here the position
  is a turn boundary — the end of a user message. Same "activation at the end of
  this context" structure, different region. The numbers in RESULTS.md were not
  measured at turn boundaries.
- **Multi-turn is a different shape from the corpus.** The experiment is strictly
  one user prompt and one Gemma response. Past turn 2 you are in a context shape
  nothing here was measured on.

## Files

| | |
|---|---|
| `app.py` | the web front end. Stdlib `http.server` only — no framework, no new dependency |
| `session.py` | the conversation: activation capture, generation, and the set arithmetic |
| `trust_report.py` | the original command-line tool, over a stored corpus |

`session.py` and `trust_report.py` both import `nla_av`, `sampling` and
`hf_paths` from [`../src/`](../src/), and the upstream `nla/` package via
`NLA_REPO`.
